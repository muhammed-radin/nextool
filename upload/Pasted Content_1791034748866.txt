# 1. PRE-PLAN RECOVERY — FAILED STEP MUST CREATE A RECOVERY SUBGOAL

Current pre-plan behavior:

```text
Main Goal
   ↓
Pre-plan multiple steps
   ↓
Execute steps
   ↓
One step fails
   ↓
Entire task stops
```

Change this only for:

```text
plannerType = pre-plan
```

Do not change the one-by-one planner behavior from v1.0.10.

---

# 2. NEW PRE-PLAN FAILURE RECOVERY FLOW

When a pre-planned step fails or produces an unexpected/unusable result:

```text
MAIN GOAL
   ↓
PRE-PLAN
   ↓
STEP 1
   ↓
STEP 2 ← failure / unexpected response
   ↓
STOP NORMAL PLAN TEMPORARILY
   ↓
OBSERVE FAILURE
   ↓
CREATE RECOVERY SUBGOAL
   ↓
PRE-PLAN RECOVERY SUBGOAL
   ↓
EXECUTE RECOVERY STEPS
   ↓
RECOVERY SUCCESS?
 ┌───────────────┐
 │ YES           │ NO
 ↓               ↓
RESTORE         RETRY / REPLAN
MAIN FLOW       RECOVERY
 ↓               ↓
CONTINUE        ATTEMPTS
MAIN PLAN        ↓
                MAX ATTEMPTS
                ↓
              END TASK
```

The original main goal remains intact.

The main pre-plan is not discarded merely because one step failed.

---

# 3. FAILURE DETECTION

Treat a pre-plan step as requiring recovery when:

```text
tool execution failed
tool timeout
tool returned an error
unexpected response
invalid/unusable result
verification failed
required expected state was not reached
observer determines the step outcome is not usable
```

Do not classify ordinary expected intermediate results as failures.

The Observer should remain the authority for determining whether the result is acceptable.

---

# 4. FREEZE THE MAIN PLAN DURING RECOVERY

When a planned step fails:

```text
Main plan:
✓ Step 1
✗ Step 2
○ Step 3
○ Step 4
```

do not immediately execute:

```text
Step 3
```

Instead:

```text
Step 2 → recovery required
```

Create a recovery subgoal.

Example:

```text
Main Goal:
Restore API server.

Main pre-plan:
1. Check health
2. Restart service
3. Verify health
4. Report status

Step 2 fails:
permission denied
```

Create:

```text
Recovery Subgoal:
Recover from permission failure so the main service-restart goal can continue.
```

---

# 5. RECOVERY SUBGOAL MUST HAVE ITS OWN PRE-PLAN

The recovery system must use the existing pre-plan strategy.

Example:

```text
Recovery Subgoal
 ↓
Pre-plan
 ↓
1. Inspect service state
2. Check available restart method
3. Use alternate recovery tool
4. Verify service
```

Do not use the one-by-one planner for this requirement.

This feature applies only to failed **pre-plan steps**.

---

# 6. RETURN TO THE MAIN PLAN AFTER SUCCESS

When recovery succeeds:

```text
Recovery completed
        ↓
Verify main-goal state
        ↓
Restore main plan
        ↓
Determine next valid unfinished step
        ↓
Continue main goal
```

Do not restart the entire task unnecessarily.

Do not repeat already completed successful steps unless the new recovery state invalidated them.

---

# 7. MAIN PLAN MUST BE STATE-AWARE AFTER RECOVERY

Do not blindly continue at the exact array index.

Re-evaluate:

```text
completed steps
failed step
recovery results
current MainState
latest observations
goal status
remaining plan validity
```

Then determine which original main-plan steps are still relevant.

Example:

```text
Main plan:
1. inspect
2. restart
3. verify
4. report

Step 2 failed.
Recovery performed an alternate restart successfully.

After recovery:
Step 2 may already be satisfied.
```

Therefore the runtime may continue from:

```text
3. verify
```

instead of repeating step 2.

---

# 8. RECOVERY ATTEMPT LIMIT

Recovery must not loop forever.

Introduce a configurable recovery attempt limit for failed pre-plan steps.

Suggested default:

```text
4 attempts
```

Allowed range should be defined through the centralized configuration limits system.

Recommended:

```text
default = 4
min = 2
max = 4
```

The implementation must use the project's existing configuration-limits schema.

Do not hard-code the value in the task loop if a configuration-limits entry is available.

---

# 9. WHAT COUNTS AS AN ATTEMPT

An attempt means a meaningful recovery cycle:

```text
Observe
→ create/revise recovery subgoal
→ pre-plan recovery
→ execute recovery plan
→ verify
```

Do not increment the counter for:

```text
UI refresh
SSE replay
status polling
ordinary planner events
```

Do increment when an actual recovery attempt is executed.

---

# 10. RECOVERY SUCCESS

Recovery succeeds only when the Observer can establish that:

```text
the failed condition has been resolved
```

or:

```text
the main goal can safely continue
```

Do not treat merely receiving an HTTP 200 or a tool execution `completed` status as sufficient when the task requires actual state verification.

---

# 11. RECOVERY FAILURE

If the recovery subgoal fails:

```text
Attempt 1
→ fail

Attempt 2
→ fail

Attempt 3
→ fail

Attempt 4
→ fail
```

Then:

```text
Observe final failure
        ↓
record useful final state
        ↓
terminate task
```

The task must end honestly as failed/stopped according to the existing task lifecycle.

Do not continue blindly through the remaining original main-plan steps.

---

# 12. UNRECOVERABLE / UNEXPECTED RESULT

When the Observer determines that the situation cannot safely proceed:

```text
recoverability = false
```

end the task immediately.

Do not waste the remaining retry budget when recovery is clearly impossible.

# 20. NEW TOOL ENVIRONMENT — `freedom-node`

Add a new tool execution environment:

```text
freedom-node
```

This environment is intentionally different from the existing restricted environments.

Its purpose is to provide a tool with complete Node.js freedom.

It must not inherit the normal:

```text
js-function
virtual filesystem
network policy
request limits
file-entry limits
sandbox restrictions
```

unless explicitly required by another non-contradictory runtime safety mechanism.

---

# 21. FREEDOM-NODE SEMANTICS

`freedom-node` means the tool is allowed to access normal Node.js capabilities.

Examples include:

```text
fs
path
os
child_process
process
Buffer
streams
native Node modules
npm
external commands
network access
real filesystem
environment variables
```

where available to the host runtime.

The environment must be intentionally different from the existing hardened `js-function` sandbox.

---

# 22. FREEDOM-NODE MUST BE EXPLICIT

Do not silently convert existing tools to `freedom-node`.

Existing environments remain unchanged.

Only tools explicitly created/imported with:

```text
environment = "freedom-node"
```

receive these semantics.

Existing:

```text
js-function
virtual-env
dynamic
builtin
```

behavior must remain intact.

---

# 23. REAL FILESYSTEM ACCESS

`freedom-node` may access the real host filesystem.

Do not redirect its file operations into the normal NexTool virtual filesystem.

Example:

```js
import fs from "node:fs";
```

must operate against the real Node process filesystem available to the runtime.

---

# 24. NETWORK ACCESS

`freedom-node` does not use the normal Network Policy request restrictions.

It may perform normal Node network operations.

Do not silently cap it with the standard:

```text
request count
response size
redirect count
network timeout
URL import restriction
```

configuration used by restricted environments.

---

# 25. VFS CONFIGURATION REQUIREMENT

The existing centralized configuration limits system must contain separate filesystem configuration.

The user requirement is:

```text
vfs
```

for restricted virtual filesystem limits.

The unrestricted escape configuration should be represented as:

```text
fs
```

where the existing configuration architecture permits that distinction.

Do not create an unrelated third filesystem configuration system.

---

# 26. FREEDOM-NODE + `fs` CONFIGURATION

`freedom-node` must use the `fs` configuration path to determine that real filesystem restrictions are not being applied by NexTool's normal VFS limiter.

Example conceptual configuration:

```json
{
  "vfs": {
    "...": "restricted virtual filesystem limits"
  },
  "fs": {
    "enabled": true,
    "restricted": false
  }
}
```

Use the project's real configuration-limits schema rather than blindly copying this exact shape if the current file uses another structure.

The important semantics are:

```text
vfs = normal restricted tool filesystem
fs = unrestricted freedom-node filesystem mode
```


---

# 35. GLOBAL AUTO-EXECUTION — HIGHEST PRIORITY

Global Settings is the highest-priority setting.

If global auto-execution is explicitly enabled:

```text
GLOBAL = ENABLED
```

it overrides the lower-level contents/configuration.

Example:

```text
Global = ON
Tool = OFF
Task = OFF
```

Effective behavior:

```text
AUTO-EXECUTE = ON
```

The lower-level values must not override the global enable.

---

# 36. TOOL-LEVEL AUTO-EXECUTION

Each tool may have its own auto-execution setting in:

```text
Tools → Create/Edit
```

When global auto-execution does not force behavior, the tool configuration may override the Task Console setting.

Example:

```text
Global = not forcing enable
Tool = ON
Task = OFF
```

Effective behavior:

```text
AUTO-EXECUTE = ON
```

Tool-level configuration has higher precedence than the Task Console configuration.

---

# 37. TASK CONSOLE AUTO-EXECUTION

Task Console provides the lowest-level task-specific preference.

Example:

```text
Global = not forcing enable
Tool = not forcing enable
Task = ON
```

Effective:

```text
AUTO-EXECUTE = ON
```

The Task Console must not override a higher-priority global or tool-level decision.

---

Use that resolver everywhere auto-execution decisions are made.
