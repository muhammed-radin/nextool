     1→     1→# NexTool Q1 — v1.0.0
     2→     2→
     3→     3→## Master Development Prompt
     4→     4→
     5→     5→Build **NexTool Q1 v1.0.0**, a specialized AI **task-processing, decision, planning, observation, automation, and tool-execution system**.
     6→     6→
     7→     7→NexTool is **not an LLM, chatbot, conversational AI, or general-purpose text generator**.
     8→     8→
     9→     9→Its purpose is to receive a task, understand the objective and current state, plan actions, select and parameterize tools, execute asynchronous tools, observe the results, update state, create new subgoals when necessary, and continue until the objective is completed.
    10→    10→
    11→    11→The system must be designed as a real executable architecture, not a UI simulation or hardcoded demo.
    12→    12→

    85→    85→# 2. Core Architecture
    86→    86→
    87→    87→The system contains two major intelligence layers:
    88→    88→
    89→    89→```text
    90→    90→NexTool Main
    91→    91→│
    92→    92→├── Planner
    93→    93→├── Observer
    94→    94→├── State Manager
    95→    95→├── Context Manager
    96→    96→├── Memory Manager
    97→    97→├── History Manager
    98→    98→├── Goal Controller
    99→    99→├── Live Controller
   100→   100→├── Event Manager
   101→   101→├── Tool Runtime
   102→   102→└── CoreModule
   103→   103→       ├── Intent Understanding
   104→   104→       ├── Tool Matching
   105→   105→       ├── Parameter Generation
   106→   106→       └── Confidence
   107→   107→```
   108→   108→
   109→   109→## Main
   110→   110→
   111→   111→The **Main** system is the orchestration layer.
   112→   112→
   113→   113→Main is responsible for:
   114→   114→
   115→   115→* receiving requests
   116→   116→* understanding the overall objective
   117→   117→* maintaining task state
   118→   118→* creating and updating plans
   119→   119→* creating subgoals
   120→   120→* invoking CoreModule
   121→   121→* invoking tools
   122→   122→* waiting for asynchronous results
   123→   123→* observing tool outputs
   124→   124→* updating state
   125→   125→* determining whether the goal is complete
   126→   126→* handling failures
   127→   127→* continuing execution
   128→   128→* stopping execution
   129→   129→* managing Goal Mode
   130→   130→* managing Live Mode
   131→   131→* processing events
   132→   132→* processing user feedback
   133→   133→
   134→   134→Main should initially be implemented primarily with deterministic TypeScript/JavaScript orchestration logic.
   135→   135→
   136→   136→Do not create another unnecessarily large neural model for Main.
   137→   137→
   138→   138→---
   139→   139→
   140→   140→# 3. CoreModule
   141→   141→
   142→   142→CoreModule is the specialized neural component responsible for connecting a task requirement with available tools.
   143→   143→
   144→   144→CoreModule is **not merely a classifier**.
   145→   145→
   146→   146→It must support:
   147→   147→
   148→   148→1. understanding the current requested action
   149→   149→2. selecting the appropriate tool
   150→   150→3. understanding the tool schema
   151→   151→4. extracting parameters directly from the task
   152→   152→5. constructing parameters when values must be generated
   153→   153→6. detecting missing parameters
   154→   154→7. identifying ambiguity
   155→   155→8. deciding when no available tool is suitable
   156→   156→9. estimating confidence
   157→   157→10. returning structured output
   158→   158→
   159→   159→CoreModule must work with dynamically provided tools.
   160→   160→
   161→   161→Do not hardcode a fixed set of tool IDs/classes inside the model.
   162→   162→
   163→   163→---
   164→   164→
   165→   165→# 4. Natural Language Understanding
   166→   166→
   167→   167→NexTool must understand intent rather than requiring exact string matches.
   168→   168→
   169→   169→For example:
   170→   170→
   171→   171→```text
   172→   172→moniter the server
   173→   173→```
   174→   174→
   175→   175→should be understood as:
   176→   176→
   177→   177→```text
   178→   178→monitor the server
   179→   179→```
   180→   180→
   181→   181→Likewise:
   182→   182→
   183→   183→```text
   184→   184→infrom me
   185→   185→```
   186→   186→
   187→   187→should be understood as:
   188→   188→
   189→   189→```text
   190→   190→inform me
   191→   191→```
   192→   192→
   193→   193→The model should support:
   194→   194→
   195→   195→* spelling mistakes
   196→   196→* minor grammar mistakes
   197→   197→* alternative wording
   198→   198→* synonyms
   199→   199→* different sentence structures
   200→   200→* short commands
   201→   201→* long descriptions
   202→   202→* natural language variations
   203→   203→* contextual references
   204→   204→
   205→   205→Do not rely on exact keyword matching as the primary intelligence mechanism.
   206→   206→

   209→   209→# 5. Tool System
   210→   210→
   211→   211→NexTool must support dynamically registered tools.
   212→   212→
   213→   213→Every tool must expose a structured definition containing at minimum:
   214→   214→
   215→   215→```json
   216→   216→{
   217→   217→  "name": "server.health",
   218→   218→  "description": "Checks the health status of a server.",
   219→   219→  "schema": {
   220→   220→    "type": "object",
   221→   221→    "properties": {
   222→   222→      "serverId": {
   223→   223→        "type": "string",
   224→   224→        "required": true
   225→   225→      }
   226→   226→    }
   227→   227→  }
   228→   228→}
   229→   229→```
   230→   230→
   231→   231→Tool definitions may additionally contain metadata describing whether a parameter is:
   232→   232→
   233→   233→* extractive
   234→   234→* constructive
   235→   235→* optional
   236→   236→* required
   237→   237→* enum
   238→   238→* numeric
   239→   239→* string
   240→   240→* boolean
   241→   241→* object
   242→   242→* array
   243→   243→
   244→   244→Example:
   245→   245→
   246→   246→```json
   247→   247→{
   248→   248→  "name": "image.generate",
   249→   249→  "description": "Generate an image from a textual description.",
   250→   250→  "schema": {
   251→   251→    "type": "object",
   252→   252→    "properties": {
   253→   253→      "prompt": {
   254→   254→        "type": "string",
   255→   255→        "required": true,
   256→   256→        "generation": "constructive"
   257→   257→      },
   258→   258→      "size": {
   259→   259→        "type": "string",
   260→   260→        "required": false
   261→   261→      },
   262→   262→      "style": {
   263→   263→        "type": "string",
   264→   264→        "required": false,
   265→   265→        "generation": "constructive"
   266→   266→      }
   267→   267→    }
   268→   268→  }
   269→   269→}
   270→   270→```
   271→   271→
   272→   272→---
   273→   273→
   274→   274→# 6. Extractive Parameters
   275→   275→
   276→   276→CoreModule must be able to directly extract values from the request.
   277→   277→
   278→   278→Example:
   279→   279→
   280→   280→User:
   281→   281→
   282→   282→```text
   283→   283→Check the weather in Kochi
   284→   284→```
   285→   285→
   286→   286→Tool:
   287→   287→
   288→   288→```text
   289→   289→weather.get
   290→   290→```
   291→   291→
   292→   292→Parameters:
   293→   293→
   294→   294→```json
   295→   295→{
   296→   296→  "location": "Kochi"
   297→   297→}
   298→   298→```
   299→   299→
   300→   300→No unnecessary generation should occur when the information already exists in the request.
   301→   301→
   302→   302→---
   303→   303→
   304→   304→# 7. Constructive Parameters
   305→   305→
   306→   306→CoreModule must also be able to construct parameters when a tool needs generated content.
   307→   307→
   308→   308→Example:
   309→   309→
   310→   310→User:
   311→   311→
   312→   312→```text
   313→   313→Create an image of a car on a city street at night
   314→   314→```
   315→   315→
   316→   316→CoreModule may produce:
   317→   317→
   318→   318→```json
   319→   319→{
   320→   320→  "tool": "image.generate",
   321→   321→  "params": {
   322→   322→    "prompt": "A cinematic and highly detailed modern car parked on a city street at night, illuminated by street lamps, realistic urban architecture, atmospheric lighting, natural reflections on the road, realistic photography",
   323→   323→    "size": "1024x1024",
   324→   324→    "style": "photorealistic"
   325→   325→  },
   326→   326→  "confidence": 0.97
   327→   327→}
   328→   328→```
   329→   329→
   330→   330→The generated value must be based on:
   331→   331→
   332→   332→* user intent
   333→   333→* tool description
   334→   334→* parameter schema
   335→   335→* context
   336→   336→* available state
   337→   337→* previous observations
   338→   338→
   339→   339→Do not simply copy the original sentence into every constructive parameter.
   340→   340→

   346→   346→

   348→   348→
   349→   349→```json
   350→   350→{
   351→   351→  "status": "tool_call",
   352→   352→  "tool": "server.health",
   353→   353→  "params": {

   355→   355→  },
   356→   356→  "confidence": 0.96
   357→   357→}
   358→   358→```
   359→   359→
   360→   360→Supported states should include concepts such as:
   361→   361→
   362→   362→```text
   363→   363→tool_call
   364→   364→no_tool
   365→   365→clarification_required
   366→   366→cannot_execute

   371→   371→

   373→   373→
   374→   374→# 9. Tool Runtime
   375→   375→
   376→   376→Separate tool reasoning from actual tool execution.
   377→   377→
   378→   378→Architecture:
   379→   379→
   380→   380→```text
   381→   381→CoreModule
   382→   382→     ↓
   383→   383→Tool Call
   384→   384→     ↓
   385→   385→Tool Runtime
   386→   386→     ↓
   387→   387→External Function
   388→   388→```
   389→   389→
   390→   390→Tools must be asynchronous.
   391→   391→
   392→   392→Every execution must return structured state such as:
   393→   393→
   394→   394→```json
   395→   395→{
   396→   396→  "executionId": "exec_001",
   397→   397→  "status": "completed",
   398→   398→  "result": {},
   399→   399→  "error": null
   400→   400→}
   401→   401→```
   402→   402→
   403→   403→Supported execution states:
   404→   404→
   405→   405→```text
   406→   406→pending
   407→   407→running
   408→   408→completed
   409→   409→failed
   410→   410→timeout
   411→   411→cancelled
   412→   412→```
   413→   413→
   414→   414→A tool failure must become observable state.
   415→   415→
   416→   416→A failed tool must not automatically crash the entire NexTool runtime.
   417→   417→
   418→   418→---
   419→   419→
   420→   420→# 10. Parallel Tool Execution
   421→   421→
   422→   422→Independent operations may execute in parallel.
   423→   423→
   424→   424→Example:
   425→   425→
   426→   426→```text
   427→   427→Check CPU
   428→   428→Check memory
   429→   429→Check disk
   430→   430→```
   431→   431→
   432→   432→These can execute concurrently.
   433→   433→
   434→   434→But dependent operations must wait for the required result.
   435→   435→
   436→   436→Example:
   437→   437→
   438→   438→```text
   439→   439→Check server
   440→   440→     ↓
   441→   441→If unhealthy
   442→   442→     ↓
   443→   443→Restart server
   444→   444→```
   445→   445→
   446→   446→Restart must wait for the health result.
   447→   447→
   448→   448→Use asynchronous execution and dependency-aware scheduling.
   449→   449→
   450→   450→---
   451→   451→
   452→   452→# 11. Goal Mode
   453→   453→
   454→   454→Goal Mode is the default mode.
   455→   455→
   456→   456→Default configuration:
   457→   457→
   458→   458→```json
   459→   459→{
   460→   460→  "mode": "goal"
   461→   461→}
   462→   462→```
   463→   463→
   464→   464→The system must never automatically switch itself into Live Mode.
   465→   465→
   466→   466→Goal Mode performs finite task execution:
   467→   467→
   468→   468→```text
   469→   469→REQUEST
   470→   470→ ↓
   471→   471→PLAN
   472→   472→ ↓
   473→   473→EXECUTE
   474→   474→ ↓
   475→   475→WAIT
   476→   476→ ↓
   477→   477→OBSERVE
   478→   478→ ↓
   479→   479→UPDATE
   480→   480→ ↓
   481→   481→CHECK GOAL
   482→   482→ ↓
   483→   483→COMPLETE?
   484→   484→ ├── YES → FINAL RESULT
   485→   485→ └── NO  → REPLAN
   486→   486→```
   487→   487→
   488→   488→The task must terminate when:
   489→   489→
   490→   490→* the goal is achieved
   491→   491→* the system determines the goal cannot be achieved
   492→   492→* a required clarification is impossible
   493→   493→* a configured safety/limit condition is reached
   494→   494→* the user explicitly stops the task
   495→   495→
   496→   496→---
   497→   497→
   498→   498→# 12. Dynamic Subgoals
   499→   499→
   500→   500→Main must be able to create subgoals dynamically from observations.
   501→   501→
   502→   502→Example:
   503→   503→
   504→   504→User:
   505→   505→
   506→   506→```text
   507→   507→Monitor the server, notify me if it becomes unhealthy, and try to restore it.
   508→   508→```
   509→   509→
   510→   510→Possible execution:
   511→   511→
   512→   512→```text
   513→   513→Root Goal:
   514→   514→Monitor and restore server
   515→   515→
   516→   516→Subgoal:
   517→   517→Check server health
   518→   518→
   519→   519→Observation:
   520→   520→API unhealthy
   521→   521→
   522→   522→New Subgoal:
   523→   523→Diagnose API
   524→   524→
   525→   525→Observation:
   526→   526→Service process stopped
   527→   527→
   528→   528→New Subgoal:
   529→   529→Restart service
   530→   530→
   531→   531→Observation:
   532→   532→Service restarted
   533→   533→
   534→   534→New Subgoal:
   535→   535→Verify health
   536→   536→
   537→   537→Observation:
   538→   538→Healthy
   539→   539→
   540→   540→New Subgoal:
   541→   541→Notify user
   542→   542→```
   543→   543→
   544→   544→Subgoals must not require all possible steps to be predetermined.
   545→   545→
   546→   546→Observations may create new actions.
   547→   547→
   548→   548→---
   549→   549→
   550→   550→# 13. Goal Completion
   551→   551→
   552→   552→Goal completion must be based on actual state, not merely on successful tool execution.
   553→   553→
   554→   554→For example:
   555→   555→
   556→   556→```text
   557→   557→restart.server → completed
   558→   558→```
   559→   559→
   560→   560→does NOT necessarily mean:
   561→   561→
   562→   562→```text
   563→   563→server recovered → true
   564→   564→```
   565→   565→
   566→   566→NexTool must verify the desired state when required.
   567→   567→
   568→   568→Example:
   569→   569→
   570→   570→```text
   571→   571→Restart server
   572→   572→     ↓
   573→   573→Observe server
   574→   574→     ↓
   575→   575→Health check
   576→   576→     ↓
   577→   577→Healthy?
   578→   578→     ├── YES → goal complete
   579→   579→     └── NO  → continue diagnosis/recovery
   580→   580→```
   581→   581→
   582→   582→---
   583→   583→
   584→   584→# 14. Live Mode
   585→   585→
   586→   586→Live Mode must only be enabled explicitly.
   587→   587→
   588→   588→Example:
   589→   589→
   590→   590→```json
   591→   591→{
   592→   592→  "mode": "live"
   593→   593→}
   594→   594→```
   595→   595→
   596→   596→Live Mode is intended for continuous tasks.
   597→   597→
   598→   598→It is not simply an infinite loop.
   599→   599→
   600→   600→It is a combination of:
   601→   601→
   602→   602→* scheduled execution
   603→   603→* event-driven execution
   604→   604→* observation
   605→   605→* reaction
   606→   606→* replanning
   607→   607→* user feedback
   608→   608→* continuous state management
   609→   609→
   610→   610→Example:
   611→   611→
   612→   612→```text
   613→   613→Task:
   614→   614→Monitor server health continuously.
   615→   615→
   616→   616→Interval:
   617→   617→1 hour
   618→   618→```
   619→   619→
   620→   620→NexTool checks every hour.
   621→   621→
   622→   622→However:
   623→   623→
   624→   624→```text
   625→   625→00:00 → scheduled check
   626→   626→01:00 → scheduled check
   627→   627→02:00 → scheduled check
   628→   628→```
   629→   629→
   630→   630→If the server crashes at:
   631→   631→
   632→   632→```text
   633→   633→02:27
   634→   634→```
   635→   635→
   636→   636→an event should wake NexTool immediately.
   637→   637→
   638→   638→It must not wait until:
   639→   639→
   640→   640→```text
   641→   641→03:00
   642→   642→```
   643→   643→

   655→   655→* external system event
   656→   656→* environment state change
   657→   657→* user message
   658→   658→* user correction
   659→   659→* user feedback
   660→   660→* emergency notification
   661→   661→
   662→   662→Architecture:
   663→   663→
   664→   664→```text
   665→   665→Event Source
   666→   666→     ↓
   667→   667→Event Manager
   668→   668→     ↓
   669→   669→Observer
   670→   670→     ↓
   671→   671→Planner
   672→   672→     ↓
   673→   673→CoreModule
   674→   674→     ↓
   675→   675→Tools
   676→   676→     ↓
   677→   677→Environment
   678→   678→     ↓
   679→   679→Observer
   680→   680→```
   681→   681→
   682→   682→Multiple event sources must be supported.
   683→   683→

   685→   685→
   686→   686→# 16. Live Mode User Feedback
   687→   687→
   688→   688→A user must be able to correct NexTool.
   689→   689→
   690→   690→Example:
   691→   691→
   692→   692→```text
   693→   693→NexTool:
   694→   694→Restarting service A.
   695→   695→```
   696→   696→
   697→   697→User:
   698→   698→
   699→   699→```text
   700→   700→Incorrect decision.
   701→   701→Service B is the actual failing service.
   702→   702→```
   703→   703→
   704→   704→This becomes a feedback event.
   705→   705→
   706→   706→The runtime should:
   707→   707→
   708→   708→1. receive the event
   709→   709→2. record it
   710→   710→3. update current state/context
   711→   711→4. adapt the current plan
   712→   712→5. revise the active subgoal if necessary
   713→   713→6. continue execution
   714→   714→
   715→   715→User feedback must not be ignored simply because a task is already running.
   716→   716→

   719→   719→# 17. Live Mode Context
   720→   720→
   721→   721→Live Mode should not repeatedly process the entire world state unnecessarily.
   722→   722→
   723→   723→The model should use:
   724→   724→
   725→   725→```text
   726→   726→Previous Context
   727→   727→+
   728→   728→Changes / Delta
   729→   729→+
   730→   730→New Observation
   731→   731→+
   732→   732→Relevant Memory
   733→   733→+
   734→   734→Relevant History
   735→   735→```
   736→   736→
   737→   737→Example:
   738→   738→
   739→   739→```json
   740→   740→{
   741→   741→  "previousContext": {},
   742→   742→  "delta": {},
   743→   743→  "observation": {},
   744→   744→  "memory": {},
   745→   745→  "history": []
   746→   746→}
   747→   747→```
   748→   748→
   749→   749→The system must be capable of identifying what actually changed.
   750→   750→
   751→   751→---
   752→   752→
   753→   753→# 18. Persistent Memory
   754→   754→
   755→   755→Persistent Memory stores long-term information.
   756→   756→
   757→   757→Examples:
   758→   758→
   759→   759→```text
   760→   760→Preferred server
   761→   761→Known device IDs
   762→   762→User preferences
   763→   763→Past successful strategies
   764→   764→Important configuration
   765→   765→Long-term task information
   766→   766→```
   767→   767→
   768→   768→Memory must be separated from live environment state.
   769→   769→
   770→   770→---
   771→   771→
   772→   772→# 19. Live State
   773→   773→
   774→   774→Live State represents the current environment and task state.
   775→   775→
   776→   776→Examples:
   777→   777→
   778→   778→```text
   779→   779→serverStatus = unhealthy
   780→   780→temperature = 74
   781→   781→battery = 31%
   782→   782→currentTask = recovery
   783→   783→activeSubgoal = restart_service
   784→   784→```
   785→   785→
   786→   786→Live State may change frequently.
   787→   787→
   788→   788→Persistent Memory should not be treated as the same thing as Live State.
   789→   789→
   790→   790→---
   791→   791→
   792→   792→# 20. Memory + Adaptation
   793→   793→
   794→   794→Live Mode supports two concepts:
   795→   795→
   796→   796→### A. Remember
   797→   797→
   798→   798→Store useful information for future execution.
   799→   799→
   800→   800→### B. Adapt
   801→   801→
   802→   802→Use new observations and feedback to alter future decisions.
   803→   803→
   804→   804→Version 1.0.0 does not require automatic modification of neural network weights during runtime.
   805→   805→
   806→   806→Adaptation may happen through:
   807→   807→
   808→   808→* state updates
   809→   809→* memory updates
   810→   810→* context updates
   811→   811→* history
   812→   812→* strategy adjustments
   813→   813→* feedback records
   814→   814→* future training datasets
   815→   815→
   816→   816→---
   817→   817→
   818→   818→# 21. Reasoning Level
   819→   819→
   820→   820→Every request may specify a reasoning level from:
   821→   821→
   822→   822→```text
   823→   823→1 → 6
   824→   824→```
   825→   825→
   826→   826→Conceptual behavior:
   827→   827→
   828→   828→```text
   829→   829→1 = ultra-fast
   830→   830→2 = very fast
   831→   831→3 = fast
   832→   832→4 = balanced
   833→   833→5 = deep
   834→   834→6 = maximum reasoning
   835→   835→```
   836→   836→
   837→   837→Do not create six separate models merely because the UI contains six levels.
   838→   838→
   839→   839→Reasoning level may control:
   840→   840→
   841→   841→* planning depth
   842→   842→* number of candidate tools
   843→   843→* verification passes
   844→   844→* confidence thresholds
   845→   845→* number of retries
   846→   846→* parameter refinement
   847→   847→* observation depth
   848→   848→* subgoal analysis
   849→   849→* result validation
   850→   850→* re-evaluation passes
   851→   851→
   852→   852→The implementation should benchmark latency versus quality.
   853→   853→
   854→   854→---

   972→   972→# 25. Neural Architecture
   973→   973→
   974→   974→Use **TensorFlow.js**.
   975→   975→
   976→   976→Node.js backend should support:
   977→   977→
   978→   978→```text
   979→   979→@tensorflow/tfjs-node
   980→   980→```
   981→   981→
   982→   982→Browser compatibility should remain possible where practical.
   983→   983→
   984→   984→The model should be custom and lightweight.
   985→   985→
   986→   986→Do not build a giant LLM.
   987→   987→
   988→   988→Initial architecture should be benchmark-driven.
   989→   989→
   990→   990→Possible baseline:
   991→   991→
   992→   992→```text
   993→   993→Input Representation
   994→   994→        ↓
   995→   995→Shared Encoder
   996→   996→        ↓
   997→   997→Hidden Layer
   998→   998→        ↓
   999→   999→Hidden Layer
  1000→  1000→        ↓
  1001→  1001→Hidden Layer
  1002→  1002→        ↓
  1003→  1003→Hidden Layer
  1004→  1004→        ↓
  1005→  1005→Multiple Heads
  1006→  1006→ ├── Tool Matching
  1007→  1007→ ├── Parameter Generation
  1008→  1008→ └── Confidence
  1009→  1009→```
  1010→  1010→
  1011→  1011→Baseline candidate:
  1012→  1012→
  1013→  1013→```text
  1014→  1014→4 hidden layers
  1015→  1015→256 units
  1016→  1016→GELU or ReLU
  1017→  1017→```
  1018→  1018→
  1019→  1019→Benchmark alternatives:
  1020→  1020→
  1021→  1021→```text
  1022→  1022→Tiny:
  1023→  1023→2 × 128
  1024→  1024→
  1025→  1025→Small:
  1026→  1026→3 × 256
  1027→  1027→
  1028→  1028→Baseline:
  1029→  1029→4 × 256
  1030→  1030→
  1031→  1031→Medium:
  1032→  1032→6 × 256
  1033→  1033→
  1034→  1034→Large:
  1035→  1035→6 × 512
  1036→  1036→```
  1037→  1037→
  1038→  1038→These are benchmark candidates, not fixed requirements.
  1039→  1039→
  1040→  1040→Choose the smallest architecture that provides sufficient performance.
  1041→  1041→
  1042→  1042→Do not invent a final parameter count before the input/output representation is finalized.
  1043→  1043→

  1073→  1073→# 27. Tool Matching
  1074→  1074→
  1075→  1075→CoreModule should compare the requested operation with the available tool descriptions.
  1076→  1076→
  1077→  1077→Example:
  1078→  1078→
  1079→  1079→```text

  1083→  1083→Tools:
  1084→  1084→
  1085→  1085→notification.email
  1086→  1086→sms.send
  1087→  1087→server.health
  1088→  1088→server.restart
  1089→  1089→```
  1090→  1090→
  1091→  1091→The model should identify:
  1092→  1092→
  1093→  1093→```text
  1094→  1094→server.health
  1095→  1095→notification.email
  1096→  1096→```
  1097→  1097→
  1098→  1098→as relevant depending on the current execution step.
  1099→  1099→
  1100→  1100→It should not simply return one hardcoded class for the entire system.
  1101→  1101→
