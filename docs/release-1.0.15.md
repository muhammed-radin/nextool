# NexTool v1.0.15 — THE LEARNED MIND

v1.0.15 makes the trained model a first-class part of the runtime, teaches it the
expanded v1.0.4 curriculum, exports the checkpoint in both real formats, completes
the three-way tool approval, ships a REAL interactive FS terminal and closes the
user-event delivery gaps.

- Application version: **1.0.15** (`src/lib/nexool/version.ts` — single source of truth, read dynamically everywhere)
- Trained model version: **1.0.4** (`TRAINED_MODEL_VERSION`) — separate concept from the app version
- CoreModule engine: llm-core 1.0.0 (provider-served, not retrained)
- Checkpoint: `model-checkpoints/v1.0.4/` → `model.zip` (TFJS native) + `model.nextool` (+ `tfjs/`, `nextool/` copies)

### Featurization upgrade — bigrams

`vectorize()` now hashes **adjacent-token bigrams** in addition to unigrams
(`engine.ts`). Within-family requests ("show the contents of X" vs "show the
metadata of X" vs "does X exist") share nearly identical vocabulary — bigrams
carry the word-order signal that separates them. Training and every inference
path import the SAME function, so featurization can never drift between train
and serve.

### Engine upgrade — configurable capacity

`hiddenUnits` (8-512, default 64) joins `TrainingConfig`; the CLI exposes
`--vocab` and `--hidden-units`. Final run: **vocab 1024, hidden 128, batch 16,
lr 0.004, early stop 12** → 135,457 parameters, 33 classes (all registered
tools — v1.0.3 only knew 25 of 33).

### §53 improvement loop (measured, not assumed)

| Pass | Change | Test-split tool accuracy |
| --- | --- | --- |
| 1 | unigram, vocab 512 | 54% (70 cases) |
| 2 | + 52 confusion-pair examples (typo/paraphrase hardening) | 51% (74 cases — harder split) |
| 3 | + bigram featurization | 57% |
| 4 | vocab 1024 | **59%** |

All passes are recorded in the benchmark run history (`nextool benchmark`).
The canonical checkpoint is selected by best validation accuracy, consistent
with the engine's checkpoint-selection strategy.

## 2. Current-model registry + runtime integration

v1.0.14 had **no current-model pointer** (`ModelRecord.status` allowed
'active' but nothing ever wrote it; trained models were benchmark-only).
v1.0.15:

- `src/lib/nexool/training/current-model.ts` — `markModelCurrent()` (demotes
  every other active checkpoint, promotes exactly one), `getActiveTrainedModel()`
  and a cached runtime classifier (`suggestToolFromTrainedModel`).
- Training completion **automatically marks the fresh checkpoint CURRENT**
  (`engine.ts`, spec §29).
- `/api/models` reports `currentModel` (version, classes, params, dataset
  lineage, metrics) — distinct from the llm-core engine entry and from the
  application version.
- Models page renders a "Current trained model" card.
- **CoreModule integration (§62 — the trained model is actually used):** every
  decision asks the active checkpoint first; the suggestion travels as
  `CONTEXT.classifierHint` inside the LLM prompt, and when the LLM fails the
  classifier (confidence ≥ 0.45) becomes the FIRST fallback before the
  heuristic matcher. Decision engine string: `trained-classifier:v1.0.4`.

## 4. Tool approval — [Skip] [Reject] [Accept] (§31-§36)

- **Explicit state machine** (`types.ts`): `pending → accepted | skipped |
  rejected` (+ `cancelled` on task stop) — never a single boolean.
- **SKIP** — the tool is NOT executed, the execution row records `skipped`
  (`SKIPPED_BY_USER`) and the plan CONTINUES to the next logical step. The
  planner receives "Tool X was skipped by the user — continue with the next
  logical step." A skip never burns the v1.0.13 denial ladder.
- **REJECT** — the execution is blocked (`tool.execution.blocked`,
  `user_denied`) and the v1.0.13 escalation ladder applies (#1 understand →
  #2 change plan → #3 final revision → #4 stop). The rejection reason travels
  as feedback.
- **ACCEPT** — the tool executes normally and the plan continues.
- **Approval card** (`src/components/console/approval-card.tsx`, shared by
  Live Monitor + Task Preview): tool name, environment badge, registry
  description, WHY it is requested (purpose), the target command/working
  directory (the fs.cmd `reason` block — finally rendered), params JSON,
  optional feedback, and the three buttons [Skip] [Reject] [Accept].
- **History** — every decision is persisted as a HistoryEntry row
  (`skipped` / `cancelled` + decision metadata), so the operator and the
  planner context can audit it.
- **Planner context** — skipped/rejected executions now reach `knownFailures`
  (the v1.0.14 filter that dropped `cancelled` rows is fixed), so the planner
  never repeats a rejected request and never assumes a skipped step succeeded.
- Parallel batches: skip/reject are handled per member with observable
  `planner.partial_failure` events for both.

## 5. REAL FS terminal (§37-§43)

The FS Inspector terminal is no longer a one-shot command box:

- **Real processes** — each session is a persistent interactive
  `bash --noprofile --norc -i` (own process group, `detached`), spawned by
  `src/lib/nexool/inspector/terminal-sessions.ts`.
- **Streaming** — stdout/stderr chunks stream over SSE
  (`/api/inspector/terminal/stream?sessionId=…`) while the command runs, with
  replay-on-connect, heartbeats and a seq-numbered ring buffer.
- **stdin** — every input line reaches the process; INTERACTIVE commands
  (`read`, confirmation prompts, `npm init`) work; the input placeholder
  switches to "stdin — type input for the running program…" while busy.
- **Ctrl+C / interrupt** — SIGINT to the child process group + `\x03` on
  stdin; the shell survives and returns to its prompt.
- **cwd tracking** — `PROMPT_COMMAND` emits a `__NEXOOL_CWD__cwd|exit__`
  marker (parsed + stripped server-side), so `cd` persists correctly across
  commands and exit codes surface as `[exit N]` lines (the v1.0.14 broken
  client-only cd tracking is gone).
- **Lifecycle** — `starting → running → exited | stopped | failed` with PID,
  cwd, start time and exit code displayed; 10-min idle / 30-min lifetime
  watchdogs kill leaked shells.
- **Sessions/tabs** — up to 4 server sessions, new/restart/clear/close,
  active-session switching, per-session command history (↑/↓), auto-scroll
  with manual override ("↓ jump to bottom" chip), copy output, Ctrl+L clear.
- **REAL FILESYSTEM** — the badge says "REAL FILESYSTEM — real bash
  processes"; the MCP environment has no route here (VFS-only, unchanged).
- The VFS terminal keeps the sandboxed interpreter and its VFS-only boundary.

## 6. Real-FS search fix (§30)

Root cause: the FS Inspector LANDS on the real-FS root, whose canonical
relative path is `''` — the search route treated that as a missing value and
threw `"path" must be a non-empty string.` (INVALID_PARAMS). Fixed at both
layers:

- server: empty/missing path → search from the FS root (`'.'` / VFS `'/'`);
  wrong TYPES still get a structured error (§30.2);
- client: sends the environment root explicitly.

Verified: root search, subdirectory search, depth, filename pattern, empty
result, invalid path (structured error), relative + absolute paths.

## 7. User events verified end-to-end (§44-§49)

- **Live tasks** (verified flow): Assistant `user.message` → `POST
  /api/tasks/{id}/event` → `injectEvent` → lifecycle `received → admitted` →
  `handle.wake` interrupts the wait IMMEDIATELY → queue/admission rules
  (v1.0.14 §2.2) → CoreModule (with the v1.0.4 hint) → AskSelf/tool →
  response. Corrections (`user.feedback`) trigger immediate revision cycles.
- **Goal tasks (fixed)** — admitted events were a black hole: `runGoalMode`
  never drained the inbox. Now every iteration boundary drains the inbox and
  user messages become first-class observations that steer the next step.
- **No silent limbo (fixed)** — events injected into a task with NO runtime
  handle (completed task / restart) are now observably REJECTED with a reason
  instead of persisting without a lifecycle verdict.
