# Skills — portable SKILL.md workflows (v1.0.16)

A **skill** is a folder whose `SKILL.md` teaches the AI HOW to perform a
workflow. A **tool** is a callable capability that PERFORMS an operation. The
distinction is architectural:

```text
Skill = instructions for how/when to perform a workflow
Tool  = callable capability that performs an operation
```

A skill may explain how to combine existing tools; it never creates one. A
referenced tool is used only when it actually exists and is allowed for the
current task.

## Layout

```text
skills/
├── skills.md                 ← auto-generated CATALOG (index of all skills)
├── .state.json               ← enable/disable state (survives restarts)
├── web-search/
│   ├── SKILL.md              ← the skill entrypoint (YAML frontmatter + body)
│   └── references/
│       └── search-guidelines.md
├── code-review/
│   ├── SKILL.md
│   └── references/review-checklist.md
└── debugging/
    └── SKILL.md
```

`skills.md` (the catalog) is regenerated by the registry on every change and
documents the system + all installed skills. Each skill's own `SKILL.md` is
its entrypoint — the two file names are intentionally distinct.

## SKILL.md format

```md
---
name: web-search
description: Research current topics using available web-search tools, verify sources, and prepare evidence-based answers.
---

# Web Search

Instructions for performing research...
```

- `name` (required): 3-64 chars, lowercase letters/digits/hyphens, unique.
- `description` (required): 12-500 chars — this is what CoreModule/Planner sees
  during selection.
- Optional extra frontmatter keys are tolerated but only the two required keys
  are validated. Malformed frontmatter reports a useful, specific error in the
  Skills UI and the skill is excluded from selection.

## Progressive loading (the performance contract)

1. **Discover** installed skills (directory scan, cached 2 s).
2. **Metadata only**: name + description — no bodies in discovery results.
3. **Select**: the runtime scores the task request against name+description
   (token overlap + stem-aware name matching) and picks the top ≤3 skills.
4. **Load**: FULL `SKILL.md` bodies load ONLY for selected skills (≤4, 6 KB
   cap each) and travel as a delimited USER block — the same hierarchy as task
   instructions (system constraints always win).
5. **Resources** (`references/…`) are read only when the workflow needs them,
   via the confined resource endpoint.
6. **Record**: the task emits `skills.selected` with what was selected and
   what is installed.

Selection is deterministic and observable — the same request always selects
the same skills for the same registry state.

## Management (Skills view)

| Action | How |
| --- | --- |
| View installed skills | Skills view cards (metadata, flags, validity) |
| Open details / edit | card "Open" → SKILL.md editor → Save (registry rescans) |
| Create | "New skill" → name + description + body (validated) |
| Import | "Import ZIP" — ONE top-level folder with a valid SKILL.md |
| Export | card "Export" → `<name>.zip` (folder content) |
| Enable/disable | card toggle (state persists in `.state.json`) |
| Validate | frontmatter errors shown per skill (detail + list badge) |
| Reload | "Reload" — force rescan + catalog refresh |

## Security (untrusted content)

- Skill content is INSTRUCTIONS ONLY. It can never override system-level
  constraints, environment boundaries (`fs` / `vfs` / `mcp`), explicit
  approval requirements or execution permissions.
- `scripts/` shipped with a skill are NEVER auto-executed; scripts require the
  existing tool/runtime permission and approval paths like everything else.
- Resource reads are confined to the skill's own directory (`..` escapes and
  absolute paths are refused; 256 KB per-resource cap).
- ZIP import validates the folder shape, refuses zip-slip entries and rejects
  name collisions.
- Disabling a skill removes it from selection immediately.

## Built-in skills

- **web-search** — real research workflow: decide whether external info is
  needed → search with the tools ACTUALLY available in this installation →
  prefer authoritative recent sources → open and inspect pages → cross-check →
  cite → report uncertainty. It explicitly reports the limitation when no
  functioning web-search capability exists in the installation and never
  invents results, URLs or citations.
- **code-review** — systematic review passes (correctness → security → error
  handling → performance → readability) with a prioritized, actionable report.
- **debugging** — reproduce first, read the real error, one hypothesis at a
  time, fix the root cause, verify the fix (behavior, not a clean build).

## API

| Endpoint | Purpose |
| --- | --- |
| `GET /api/skills` | metadata list (+ counts, catalog path) |
| `POST /api/skills` | `{action:'create',…}` or `{action:'reload'}` |
| `GET /api/skills/{name}` | full detail (`?resource=references/x.md` for a confined resource read) |
| `PUT /api/skills/{name}` | `{content}` (SKILL.md rewrite) and/or `{enabled}` |
| `DELETE /api/skills/{name}` | delete the skill folder |
| `GET /api/skills/{name}/export` | ZIP download |
| `POST /api/skills/import` | multipart ZIP import |

CLI parity for export/import uses the same registry paths as the API and UI.
