Expand the capabilities available to:

The goal is to provide useful application/runtime functionality while keeping the execution environment isolated from the NexTool application's real source filesystem and host system.

Both environments must support a common safe baseline where practical.

2. Expand the Node.js Tool Environment

The v1.0.5 "nodejs" environment must become a useful but restricted Node.js-compatible tool runtime.

The user should be able to use:

require()
import()
Node.js APIs
virtual filesystem
HTTP/HTTPS
child_process

where explicitly supported.

However, the environment must never receive unrestricted access to the NexTool host filesystem or application source.

---

2.1 Virtual Filesystem

Create a real Virtual File System (VFS) for NexTool tools.

This filesystem belongs to the tool runtime, not the NexTool project itself.

Example:

/vfs/
├── input/
├── output/
├── tmp/
├── data/
└── workspace/

The exact structure can be improved.

---

2.2 Why Virtual FS Exists

The purpose of VFS is to prevent tools from accidentally damaging:

NexTool source code
Next.js application files
database files
node_modules
environment files
configuration files
host filesystem

Tools should operate inside their own isolated filesystem.

---

2.3 Virtual FS Operations

Provide normal useful filesystem functionality inside the VFS.

Where supported, implement operations such as:

readFile
writeFile
appendFile
mkdir
readdir
stat
lstat
exists
rename
copy
unlink
rm
realpath

and useful path utilities.

Both callback and Promise APIs may be provided where useful, but Promise-based APIs should be preferred for modern tools.

---

2.4 "fs" Must Mean Virtual FS

Inside the Node.js environment:

const fs = require("fs");

must resolve to the NexTool Virtual FS implementation, not the host's real "fs".

Likewise:

import fs from "fs";

or supported equivalent imports must resolve to the virtualized implementation.

Do NOT give tool code direct access to the application's actual filesystem.

---

2.5 Reject Main Filesystem Access

If a tool attempts to escape the VFS and access the NexTool application's real filesystem:

process.cwd()
../
absolute host paths
application source directories
node_modules outside approved virtual/runtime packages
.env
database files

or any equivalent escape path:

reject the operation.

Return a clear runtime error.

Example:

VirtualFSAccessError:
Access to the NexTool host filesystem is not permitted.

Do not silently redirect dangerous access attempts.

---

2.6 Path Traversal Protection

Protect against:

../
../../
absolute paths
symbolic-link escapes
URL filesystem paths
encoded traversal

Normalize and validate every VFS path.

A tool must never escape its assigned virtual root.

---

2.7 Fully Functional VFS

The VFS must not be a fake API that simply returns placeholders.

It must actually store and retrieve tool files.

Support:

create
read
update
delete
list
rename
copy
metadata

where appropriate.

---

2.8 VFS Persistence

Define clear VFS lifecycle behavior.

A tool should have a controlled workspace.

Document whether files are:

per execution
per task
per session
persistent per tool

Choose the appropriate model for NexTool and implement it consistently.

If persistence is enabled, isolate each tool/task workspace from other tools.

---

2.9 VFS Size Limits

Implement safety limits such as:

maximum total VFS size
maximum file size
maximum file count
maximum path length
maximum read size
maximum write size

These values must be configurable or centrally defined.

modify NexTool source

Implement a controlled command policy.

4.3 No Host Shell Escape

  "autoExecute": false
}

9.3 Global Setting

Auto-Execute Tools

false

global autoExecute = true
    ↓

    ↓
tools execute automatically

use individual tool configuration

9.4 Configuration Precedence

    ↓
Per-Task configuration where explicitly supported

Do not allow different frontend/backend interpretations.

9.7 Approval Timeout

Maximum approval waiting time:

approval timeout

---

9.8 Explicit Deny

If the user chooses:

Deny

do not execute the tool.

Record:

---

9.9 Optional User Feedback After Denial

After denial, optionally allow the user to provide feedback.

Example:

If feedback is provided:

User feedback
 ↓

 ↓

---

9.10 Denied Tool Behavior

For an explicit user denial:

Tool NOT executed
 ↓
Record denial
 ↓
Optional feedback event
 ↓
Mark tool as skipped/rejected by user
 ↓
Continue according to task plan

Do not execute it later automatically during the same approval request.

---

9.11 Approval Rejection vs Timeout

Differentiate:

Explicit Deny

The user actively denied execution.

→ skip this tool
→ continue according to the task plan

Approval Timeout

No decision within five minutes.

→ stop task

Runtime/Safety Rejection

The system rejects execution because of a security/policy/runtime problem.

→ stop task

This distinction must be visible in task events.

---

9.12 Dependency Behavior

If a denied tool is required for a later step:

the Planner/Observer must recognize that dependency is unavailable.

Do not blindly continue as though the tool executed successfully.

For independent steps, continue where possible.

For dependent steps, replan or terminate according to the task state.

---

9.13 Approval in Parallel Execution

If multiple independent tools require approval simultaneously:

Tool A → approval
Tool B → approval
Tool C → auto-execute

support the configured parallel approval/runtime policy.

Do not automatically execute a blocked tool simply because another tool was approved.

10. Multiple Live Events

Currently Live Mode processes only one relevant event at a time.

Add a configuration:

Allow Multiple Events at Same Time

Also expose a user-friendly label:

Read & Act All Events

The two labels should refer to the same underlying configuration if both are shown.

---

10.1 Default

Preserve current behavior by default:

false

When false:

listen to one event
process it
act
continue

Other simultaneous events may be skipped/ignored according to the existing behavior.

Do not force the runtime to process every event.

---

10.2 Multiple Event Mode

When:

Allow Multiple Events at Same Time = true

Live Mode must listen for all events arriving while it is active.

Events must be stored in a queue.

Example:

Event A
Event B
Event C
Event D

becomes:

Event Queue
[ A ][ B ][ C ][ D ]

---

10.3 Sequential Event Processing

Even though events are accepted concurrently, process them one-by-one.

Example:

Queue:
A → B → C

Observer(A)
 ↓
Does action need to happen?
 ↓
Planner creates subgoal
 ↓
CoreModule
 ↓
Tools
 ↓
Finish A

Observer(B)
 ↓
...
Finish B

Observer(C)
 ↓
...

Do not process multiple event-driven action plans simultaneously unless explicitly designed later.

---

10.4 Event Queue Ordering

Preserve deterministic ordering.

Use:

priority
timestamp
sequence number

where appropriate.

Emergency/high-priority events should be processed before lower-priority queued events when the configured event policy allows it.

Do not silently reorder events without recording the reason.

---

10.5 Event Queue Persistence

The queue must be part of the task runtime state enough to survive normal UI refresh/reconnect.

If persistence is implemented, store enough metadata to recover.

Do not lose queued events merely because the frontend disconnects.

---

10.6 Event Observation

For each queued event:

Receive
 ↓
Observe
 ↓
Determine whether action is required
 ↓
If no action:
mark processed
 ↓
Next event

If action:
create subgoal
 ↓
execute
 ↓
observe result
 ↓
complete event
 ↓
next event

---

10.7 Events With No Action

If an event does not require an action:

observe
record
mark processed
move to next event

Do not create unnecessary subgoals.

---

10.8 Event UI

Show the event queue in Live Monitor and Task Preview when multiple-event mode is enabled.

Example:

Event Queue

● server.crash      Processing
○ user.feedback     Queued
○ health.changed    Queued
○ scheduled.tick    Queued

This must represent actual runtime state.

---

10.9 Event Queue Limits

Protect the runtime with configurable limits:

maximum queued events
maximum event payload size
maximum event processing time

If the queue reaches its limit, use a documented policy:

drop
coalesce
defer
stop task

Choose and implement a deterministic policy.

Do not allow unbounded memory growth.

---

10.10 Interaction With User Feedback

User feedback is itself an event.

It must enter the same event model.

If multiple-event mode is enabled:

user feedback
environment event
scheduled event

can all enter the queue and be processed according to priority/ordering.

11. Pause / Suspend Live Tasks

11.1 Pause vs Stop

Pause

Preserve:

plan

and temporarily stop new autonomous actions.

Stop

Terminates the task.

Do not confuse the two states.

---

11.2 Pause UI

Add:

---

11.3 Paused Status

Add runtime state:

paused

and show it consistently across:

Task Preview
Live Monitor
Tasks
Dashboard
terminal/checklist

Example:

● Paused

---

11.4 Pause Behavior

When paused:

no new planner actions
no new tool executions
no new scheduled autonomous actions

The task state must remain intact.

Events may either:

queue

or follow an explicitly documented pause policy.

Prefer retaining relevant events rather than silently losing them.

---

11.5 Pause Scheduler

While paused, scheduled ticks must not trigger tool actions.

The scheduler may continue tracking elapsed time, but autonomous processing must remain suspended.

When resumed, recalculate the next appropriate scheduled tick.

Do not execute a burst of missed ticks unless explicitly configured.

---

11.6 Pause During Tool Execution

If a tool is already executing when Pause is requested:

do not corrupt the execution state.

Prefer:

current atomic tool execution finishes
 ↓
task enters paused state
 ↓
no next action starts

If the tool supports safe cancellation, the runtime may cancel it, but this must be explicit and state-safe.

Never mark an incomplete execution as completed.

---

11.7 Pause During Approval

If the task is waiting for user approval and is paused:

approval remains unresolved

or is safely suspended according to the runtime design.

Do not automatically allow or deny the tool because of the pause.

The five-minute approval timeout must remain well-defined and documented.

---

11.8 Resume

When the user presses:

Resume Live

the task should continue from its preserved state:

paused
 ↓
restore state
 ↓
process queued events if applicable
 ↓
resume planner
 ↓
continue Live Mode

Do not restart the task from the beginning.

---

11.9 Pause Persistence

Persist the paused state so UI refresh/reconnection does not turn a paused task back into running.

A runtime restart should handle paused tasks safely according to the project's task persistence model.

Document any limitations honestly.
