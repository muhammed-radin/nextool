# NexTool Q1 — v1.0.0

## Master Development Prompt

Build **NexTool Q1 v1.0.0**, a specialized AI **task-processing, decision, planning, observation, automation, and tool-execution system**.

NexTool is **not an LLM, chatbot, conversational AI, or general-purpose text generator**.

Its purpose is to receive a task, understand the objective and current state, plan actions, select and parameterize tools, execute asynchronous tools, observe the results, update state, create new subgoals when necessary, and continue until the objective is completed.

The system must be designed as a real executable architecture, not a UI simulation or hardcoded demo.

---

**Name:** NexTool

# 2. Core Architecture

The system contains two major intelligence layers:

```text
NexTool Main
│
├── Planner
├── Observer
├── State Manager
├── Context Manager
├── Memory Manager
├── History Manager
├── Goal Controller
├── Live Controller
├── Event Manager
├── Tool Runtime
└── CoreModule
       ├── Intent Understanding
       ├── Tool Matching
       ├── Parameter Generation
       └── Confidence
```

## Main

The **Main** system is the orchestration layer.

Main is responsible for:

* receiving requests
* understanding the overall objective
* maintaining task state
* creating and updating plans
* creating subgoals
* invoking CoreModule
* invoking tools
* waiting for asynchronous results
* observing tool outputs
* updating state
* determining whether the goal is complete
* handling failures
* continuing execution
* stopping execution
* managing Goal Mode
* managing Live Mode
* processing events
* processing user feedback

Main should initially be implemented primarily with deterministic TypeScript/JavaScript orchestration logic.

Do not create another unnecessarily large neural model for Main.

---

# 3. CoreModule

CoreModule is the specialized neural component responsible for connecting a task requirement with available tools.

CoreModule is **not merely a classifier**.

It must support:

1. understanding the current requested action
2. selecting the appropriate tool
3. understanding the tool schema
4. extracting parameters directly from the task
5. constructing parameters when values must be generated
6. detecting missing parameters
7. identifying ambiguity
8. deciding when no available tool is suitable
9. estimating confidence
10. returning structured output

CoreModule must work with dynamically provided tools.

Do not hardcode a fixed set of tool IDs/classes inside the model.

---

# 4. Natural Language Understanding

NexTool must understand intent rather than requiring exact string matches.

For example:

```text
moniter the server
```

should be understood as:

```text
monitor the server
```

Likewise:

```text
infrom me
```

should be understood as:

```text
inform me
```

The model should support:

* spelling mistakes
* minor grammar mistakes
* alternative wording
* synonyms
* different sentence structures
* short commands
* long descriptions
* natural language variations
* contextual references

Do not rely on exact keyword matching as the primary intelligence mechanism.

# 5. Tool System

NexTool must support dynamically registered tools.

Every tool must expose a structured definition containing at minimum:

```json
{
  "name": "server.health",
  "description": "Checks the health status of a server.",
  "schema": {
    "type": "object",
    "properties": {
      "serverId": {
        "type": "string",
        "required": true
      }
    }
  }
}
```

Tool definitions may additionally contain metadata describing whether a parameter is:

* extractive
* constructive
* optional
* required
* enum
* numeric
* string
* boolean
* object
* array

Example:

```json
{
  "name": "image.generate",
  "description": "Generate an image from a textual description.",
  "schema": {
    "type": "object",
    "properties": {
      "prompt": {
        "type": "string",
        "required": true,
        "generation": "constructive"
      },
      "size": {
        "type": "string",
        "required": false
      },
      "style": {
        "type": "string",
        "required": false,
        "generation": "constructive"
      }
    }
  }
}
```

# 6. Extractive Parameters

CoreModule must be able to directly extract values from the request.

Example:

User:

```text
Check the weather in Kochi
```

Tool:

```text
weather.get
```

Parameters:

```json
{
  "location": "Kochi"
}
```

No unnecessary generation should occur when the information already exists in the request.

---

# 7. Constructive Parameters

CoreModule must also be able to construct parameters when a tool needs generated content.

Example:

User:

```text
Create an image of a car on a city street at night
```

CoreModule may produce:

```json
{
  "tool": "image.generate",
  "params": {
    "prompt": "A cinematic and highly detailed modern car parked on a city street at night, illuminated by street lamps, realistic urban architecture, atmospheric lighting, natural reflections on the road, realistic photography",
    "size": "1024x1024",
    "style": "photorealistic"
  },
  "confidence": 0.97
}
```

The generated value must be based on:

* user intent
* tool description
* parameter schema
* context
* available state
* previous observations

Do not simply copy the original sentence into every constructive parameter.

# 8. CoreModule Output

CoreModule must return machine-readable output.

Base format:

```json
{
  "status": "tool_call",
  "tool": "server.health",
  "params": {
    "serverId": "api-01"
  },
  "confidence": 0.96
}
```

Supported states should include concepts such as:

```text
tool_call
no_tool
clarification_required
cannot_execute
stop
```

The exact implementation may evolve, but the output must remain deterministic, structured, and easy for Main to process.

# 9. Tool Runtime

Separate tool reasoning from actual tool execution.

Architecture:

```text
CoreModule
     ↓
Tool Call
     ↓
Tool Runtime
     ↓
External Function
```

Tools must be asynchronous.

Every execution must return structured state such as:

```json
{
  "executionId": "exec_001",
  "status": "completed",
  "result": {},
  "error": null
}
```

Supported execution states:

```text
pending
running
completed
failed
timeout
cancelled
```

A tool failure must become observable state.

A failed tool must not automatically crash the entire NexTool runtime.

---

# 10. Parallel Tool Execution

Independent operations may execute in parallel.

Example:

```text
Check CPU
Check memory
Check disk
```

These can execute concurrently.

But dependent operations must wait for the required result.

Example:

```text
Check server
     ↓
If unhealthy
     ↓
Restart server
```

Restart must wait for the health result.

Use asynchronous execution and dependency-aware scheduling.

---

# 11. Goal Mode

Goal Mode is the default mode.

Default configuration:

```json
{
  "mode": "goal"
}
```

The system must never automatically switch itself into Live Mode.

Goal Mode performs finite task execution:

```text
REQUEST
 ↓
PLAN
 ↓
EXECUTE
 ↓
WAIT
 ↓
OBSERVE
 ↓
UPDATE
 ↓
CHECK GOAL
 ↓
COMPLETE?
 ├── YES → FINAL RESULT
 └── NO  → REPLAN
```

The task must terminate when:

* the goal is achieved
* the system determines the goal cannot be achieved
* a required clarification is impossible
* a configured safety/limit condition is reached
* the user explicitly stops the task

---

# 12. Dynamic Subgoals

Main must be able to create subgoals dynamically from observations.

Example:

User:

```text
Monitor the server, notify me if it becomes unhealthy, and try to restore it.
```

Possible execution:

```text
Root Goal:
Monitor and restore server

Subgoal:
Check server health

Observation:
API unhealthy

New Subgoal:
Diagnose API

Observation:
Service process stopped

New Subgoal:
Restart service

Observation:
Service restarted

New Subgoal:
Verify health

Observation:
Healthy

New Subgoal:
Notify user
```

Subgoals must not require all possible steps to be predetermined.

Observations may create new actions.

---

# 13. Goal Completion

Goal completion must be based on actual state, not merely on successful tool execution.

For example:

```text
restart.server → completed
```

does NOT necessarily mean:

```text
server recovered → true
```

NexTool must verify the desired state when required.

Example:

```text
Restart server
     ↓
Observe server
     ↓
Health check
     ↓
Healthy?
     ├── YES → goal complete
     └── NO  → continue diagnosis/recovery
```

---

# 14. Live Mode

Live Mode must only be enabled explicitly.

Example:

```json
{
  "mode": "live"
}
```

Live Mode is intended for continuous tasks.

It is not simply an infinite loop.

It is a combination of:

* scheduled execution
* event-driven execution
* observation
* reaction
* replanning
* user feedback
* continuous state management

Example:

```text
Task:
Monitor server health continuously.

Interval:
1 hour
```

NexTool checks every hour.

However:

```text
00:00 → scheduled check
01:00 → scheduled check
02:00 → scheduled check
```

If the server crashes at:

```text
02:27
```

an event should wake NexTool immediately.

It must not wait until:

```text
03:00
```

# 16. Live Mode User Feedback

A user must be able to correct NexTool.

Example:

```text
NexTool:
Restarting service A.
```

User:

```text
Incorrect decision.
Service B is the actual failing service.
```

This becomes a feedback event.

The runtime should:

1. receive the event
2. record it
3. update current state/context
4. adapt the current plan
5. revise the active subgoal if necessary
6. continue execution

User feedback must not be ignored simply because a task is already running.

---

# 17. Live Mode Context

Live Mode should not repeatedly process the entire world state unnecessarily.

The model should use:

```text
Previous Context
+
Changes / Delta
+
New Observation
+
Relevant Memory
+
Relevant History
```

Example:

```json
{
  "previousContext": {},
  "delta": {},
  "observation": {},
  "memory": {},
  "history": []
}
```

The system must be capable of identifying what actually changed.

---

# 18. Persistent Memory

Persistent Memory stores long-term information.

Examples:

```text
Preferred server
Known device IDs
User preferences
Past successful strategies
Important configuration
Long-term task information
```

Memory must be separated from live environment state.

---

# 19. Live State

Live State represents the current environment and task state.

Examples:

```text
serverStatus = unhealthy
temperature = 74
battery = 31%
currentTask = recovery
activeSubgoal = restart_service
```

Live State may change frequently.

Persistent Memory should not be treated as the same thing as Live State.

---

# 20. Memory + Adaptation

Live Mode supports two concepts:

### A. Remember

Store useful information for future execution.

### B. Adapt

Use new observations and feedback to alter future decisions.

Version 1.0.0 does not require automatic modification of neural network weights during runtime.

Adaptation may happen through:

* state updates
* memory updates
* context updates
* history
* strategy adjustments
* feedback records
* future training datasets

# 21. Reasoning Level

Every request may specify a reasoning level from:

```text
1 → 6
```

Conceptual behavior:

```text
1 = ultra-fast
2 = very fast
3 = fast
4 = balanced
5 = deep
6 = maximum reasoning
```

Do not create six separate models merely because the UI contains six levels.

Reasoning level may control:

* planning depth
* number of candidate tools
* verification passes
* confidence thresholds
* number of retries
* parameter refinement
* observation depth
* subgoal analysis
* result validation
* re-evaluation passes

The implementation should benchmark latency versus quality.

# 25. Neural Architecture

Use **TensorFlow.js**.

Node.js backend should support:

```text
@tensorflow/tfjs-node
```

Browser compatibility should remain possible where practical.

The model should be custom and lightweight.

Do not build a giant LLM.

Initial architecture should be benchmark-driven.

Possible baseline:

```text
Input Representation
        ↓
Shared Encoder
        ↓
Hidden Layer
        ↓
Hidden Layer
        ↓
Hidden Layer
        ↓
Hidden Layer
        ↓
Multiple Heads
 ├── Tool Matching
 ├── Parameter Generation
 └── Confidence
```

Baseline candidate:

```text
4 hidden layers
256 units
GELU or ReLU
```

Benchmark alternatives:

```text
Tiny:
2 × 128

Small:
3 × 256

Baseline:
4 × 256

Medium:
6 × 256

Large:
6 × 512
```

These are benchmark candidates, not fixed requirements.

Choose the smallest architecture that provides sufficient performance.

Do not invent a final parameter count before the input/output representation is finalized.

# 27. Tool Matching

CoreModule should compare the requested operation with the available tool descriptions.

Example:

```text

Tools:

notification.email
sms.send
server.health
server.restart
```

The model should identify:

```text
server.health
notification.email
```

as relevant depending on the current execution step.

It should not simply return one hardcoded class for the entire system.

# 29. Confidence

CoreModule should provide confidence.

Example:

```json

}
```

Confidence can influence:

* whether another reasoning pass is needed
* whether additional candidate tools are considered
* whether clarification is required
* whether verification is performed
* whether an action is allowed under configured limits

Do not assume confidence is automatically calibrated.

Evaluate it empirically.

# 79. Important Architectural Rules

Follow these rules strictly:

### Rule 1

NexTool is not a chatbot.

### Rule 2

NexTool is not an LLM.

### Rule 3

Do not replace the architecture with a generic agent framework.

### Rule 4

Do not hardcode the tool list into the model.

### Rule 5

Tools are asynchronous.

### Rule 6

Independent tools may execute in parallel.

### Rule 7

Dependent actions wait for results.

### Rule 8

Goal Mode is the default.

### Rule 9

Live Mode requires explicit user configuration.

### Rule 10

Live Mode must support scheduled and event-driven execution.

### Rule 11

Emergency events may interrupt interval waiting.

### Rule 12

User corrections must be accepted as runtime events.

### Rule 13

Persistent Memory and Live State are separate concepts.

### Rule 14

Context should use previous context + delta + new observation where appropriate.

### Rule 15

CoreModule must support both parameter extraction and parameter construction.

### Rule 16

Do not fabricate runtime results in the UI.

### Rule 17

Use real event streams for live execution visualization.

### Rule 18

Use TensorFlow.js for the neural CoreModule.

### Rule 19

Support both `.nextool` and native TensorFlow.js models.

### Rule 20

Parquet is the primary large dataset format; JSON is the interchange/debug format.

### Rule 21

Use benchmark results rather than assumptions to select the final model architecture.

### Rule 22

Build the frontend as a real Next.js application.

### Rule 23

Use Aceternity UI for the console.

### Rule 24

The Task Preview must be a dedicated screen.

### Rule 25

Live Mode output must use a terminal-style runtime view.
