2. MAJOR FEATURE — ADD A SECOND PLANNER SYSTEM

NexTool currently has a pre-planning architecture.

Current behavior:

User Goal
   ↓
Understand
   ↓
Planner creates a complete plan
   ↓
Step 1
Step 2
Step 3
Step 4
...
   ↓
Observe
   ↓
If goal already achieved:
    stop
    remaining pre-planned steps are discarded

This existing behavior is good.

Keep it.

Now add a second planner mode:

ONE-BY-ONE

The two planner strategies are:

pre-plan
one-by-one

---

3. PRE-PLAN MODE

Pre-plan remains the normal complete-plan planner.

Flow:

Understand Goal
      ↓
Build a plan containing multiple steps
      ↓
Execute first applicable step
      ↓
Observe
      ↓
Goal achieved?
 ┌───────────────┐
 │ YES           │ NO
 ↓               ↓
COMPLETE       Continue
               remaining plan
               ↓
               Observe again
               ↓
               Re-evaluate

Existing early-completion behavior must remain.

For example:

Goal:
Check whether api-01 is healthy.

Pre-plan:
1. Query server health
2. Inspect CPU
3. Inspect memory
4. Inspect service status
5. Produce final report

If step 1 already proves the goal:

server.health → healthy

the task must finish immediately.

Steps 2–5 must not execute.

The unused planned steps are simply discarded.

This behavior is intentional and must remain.

---

4. ONE-BY-ONE PLANNER

Add a completely separate planner strategy.

The one-by-one planner must not generate the entire future plan up front.

Instead:

Goal
 ↓
Understand
 ↓
Plan exactly ONE next step
 ↓
Execute ONE step
 ↓
Observe result
 ↓
Is goal achieved?
 ├── YES → COMPLETE
 └── NO
       ↓
   Understand updated state
       ↓
   Plan exactly ONE next step
       ↓
   Execute
       ↓
   Observe
       ↓
   repeat

The key difference:

PRE-PLAN

Goal
 ↓
[Step A, Step B, Step C, Step D, Step E]
 ↓
execute / observe / stop when goal achieved

ONE-BY-ONE

Goal
 ↓
[Step A]
 ↓
observe
 ↓
[Step B]
 ↓
observe
 ↓
[Step C]
 ↓
observe
 ↓
[Step D]
 ...

The second step must be generated after the result of the first step is available.

The third step must be generated after the second step's observation.

Never generate a hidden future list and pretend it is one-by-one planning.

---

5. ONE-BY-ONE PLANNING REQUIREMENTS

Each planning call must receive the latest relevant task state.

Include:

original request
current goal
current MainState
recent observations
previous executed steps
latest tool result
current task mode
reasoning level
enabled tools
known failures
known constraints

The planner should answer:

"What is the single best next step to move this task toward the goal?"

not:

"What are all steps required to finish this task?"

---

6. ONE-BY-ONE STEP CONTRACT

The planner output must contain exactly one executable planning step.

Example:

{
  "title": "Check API health",
  "detail": "Query api-01 health status before taking another action.",
  "kind": "action"
}

Do not accept:

{
  "steps": [
    {...},
    {...},
    {...}
  ]
}

for a one-by-one planning call.

If the model accidentally returns multiple steps:

sanitize
retain exactly one valid next step
discard the rest

Do not allow accidental multi-step planning to become one-by-one execution.

---

7. ONE-BY-ONE + SUBGOALS

The new planner should naturally support incremental subgoals.

Example:

Main Goal:
Restore an unhealthy production API server.

One-by-one:

Subgoal 1:
Inspect API health.

Observation:
Service is stopped.

Subgoal 2:
Restart the API service.

Observation:
Service restarted.

Subgoal 3:
Verify API health.

Observation:
Healthy.

Goal achieved → COMPLETE.

Every generated one-by-one step should be treated as the current operational subgoal.

Persist its relationship to:

main goal
task
current state
previous observation
next planning decision

Do not create independent unrelated tasks.

---

8. LIVE TASK BEHAVIOR

One-by-one planning is especially important for Live Mode.

The current Live architecture already performs observation cycles and can park in "waiting" between ticks.

Do not break that architecture.

For Live Mode:

Live Task
 ↓
Observe current world
 ↓
One-by-one planner generates ONE next action/subgoal
 ↓
Execute
 ↓
Observe
 ↓
Update MainState
 ↓
If goal/event condition requires another action:
    generate one new step
 ↓
Continue

For long-running live tasks, do not interpret the planner's finite step count as the lifetime of the live task.

A live task can continue across future ticks/events.

The one-by-one planner should make decisions based on the latest state rather than relying on stale pre-planned steps.

This is one of the primary reasons for adding this planner mode.

---

9. GOAL COMPLETION HAS PRIORITY

After every executed one-by-one step:

EXECUTE
 ↓
OBSERVE
 ↓
VERIFY GOAL

The goal verifier must run before requesting another plan.

If the goal is achieved:

COMPLETE

Do not unnecessarily call the planner again.

Do not generate:

next step

after the goal is already complete.

---

10. FAILURE HANDLING IN ONE-BY-ONE

If the current step fails:

execute
 ↓
failure
 ↓
observe failure
 ↓
replan one step

The planner should receive the failure context.

Example:

Attempt:
restart service

Result:
permission denied

Next planner input must include that failure so it can choose another appropriate action rather than blindly repeating the same step.

Prevent endless immediate repetition of an identical failed action unless the planner intentionally chooses it with new reasoning/context.
