# NexTool Q1 — Version 1.0.8

Upgrade the existing **NexTool Q1 v1.0.7** project to **v1.0.8**.

This release focuses on:

```text
Tool runtime capabilities
URL module imports
Virtual Node.js command execution
Network limits
Virtual filesystem limits
Execution limits
Centralized configurable limits
Removal of hard-coded configuration limits
Responsive Task Console cleanup
Documentation synchronization
```

Do not rebuild NexTool.

Do not remove existing functionality.

Preserve the existing architecture:

```text
Main
 ↓
Planner
 ↓
CoreModule
 ↓
Tool Runtime
 ↓
Observer
 ↓
Main
```

and the existing Goal Mode / Live Mode behavior.

---

# 1. Async `confirm()` in Both Tool Environments

Add a NexTool-provided asynchronous:

```js
await confirm("Do you want to continue?");
```

function.

It must be supported in:

```text
js-function
nodejs
```

environments.

---

## 1.1 Return Type

`confirm()` must always resolve to a boolean:

```js
const accepted = await confirm("Continue?");
```

Possible results:

```text
true
false
```

Do not return strings such as `"yes"` or `"no"`.

---

# 1.2 User Interaction

When a tool calls:

```js
await confirm("Delete the generated files?");
```

execution must pause at that point.

Show a NexTool confirmation UI.

Example:

```text
┌───────────────────────────────┐
│ Tool Confirmation             │
│                               │
│ Delete the generated files?   │
│                               │
│ [ Cancel ]       [ Confirm ]  │
└───────────────────────────────┘
```

The tool resumes only after the user responds.

---

# 1.3 Runtime Event

Treat this as a runtime interaction event.

Example:

```text
tool.confirm.requested
tool.confirm.responded
```

The event should contain enough information to associate the response with:

```text
task
execution
tool
confirmation request
```

---

# 1.4 Cancellation / Timeout

If the confirmation request is cancelled or its execution is terminated, do not leave the tool suspended forever.

Resolve according to the existing runtime cancellation semantics, preferably:

```text
false
```

for a user-facing confirmation.

Do not automatically treat an unresolved confirmation as:

```text
true
```

---

# 1.5 Tool Preview

Display confirmation requests in Task Preview / Live Monitor when they occur.

Example:

```text
[waiting] Tool confirmation requested
[waiting] Delete generated files?
```

After the user responds:

```text
[✓] Confirmation: allowed
```

or:

```text
[✓] Confirmation: denied
```

---

# 2. URL `import()` in Both Environments

Enable dynamic URL imports in:

```text
js-function
nodejs
```

Example:

```js
const module = await import("https://example.com/module.js");
```

URL imports must be real functionality, not a mocked response.

---

# 2.1 URL Import Security

URL imports must pass through the centralized NexTool network policy.

Do not bypass:

```text
allowed protocols
allowed hosts
timeout
response size
redirect limits
request limits
```

The URL import must use the same network-policy enforcement layer as `fetch` and other network operations.

---

# 2.2 Supported URL Schemes

By default support:

```text
https://
http://
```

only if the network policy allows them.

Reject unsupported protocols.

Examples:

```text
file://
data://
node://
```

must not become hidden ways to access local or host resources unless explicitly supported by the runtime.

---

# 2.3 Module Response

The downloaded resource must be interpreted as a JavaScript module.

Example:

```js
const utils = await import("https://example.com/utils.js");

return await utils.process(params.value);
```

Support:

```text
default export
named exports
multiple exports
```

where compatible with the module loader.

---

# 2.4 URL Import Isolation

Downloaded modules execute under the same sandbox/environment restrictions as the importing tool.

A URL module must NOT gain unrestricted:

```text
filesystem
process
host environment
child processes
secrets
```

access.

The imported module inherits the current tool runtime security boundary.

---

# 2.5 URL Import Limits

Apply:

```text
network timeout
maximum response size
maximum redirects
maximum network requests per execution
```

from the central configuration system described later.

---

# 2.6 URL Import Cache

If caching is implemented, cache according to the existing runtime policy.

Do not make cache behavior bypass network-policy changes.

For example, if a URL is currently blocked, a stale cached module must not automatically bypass the configured restriction.

---

# 3. Expand Virtual Node.js `child_process`

The Node.js tool environment must support substantially more commands inside the **Virtual FS**.

The goal is to allow realistic development workflows inside the isolated virtual environment.

For example, a tool should be able to create a project such as:

```text
MERN application
```

inside the Virtual FS.

It must NOT create or modify a real project on the NexTool host filesystem.

# 3.5 npm Security

# 3.6 Package Installation

When:

```bash

```

is executed, packages must be installed into the tool's isolated Virtual FS workspace.

Example:

```text

├── package.json
├── package-lock.json
└── node_modules/

```

---

# 3.7 npm Scripts

Be careful with:

```json
{
  "scripts": {
    "build": "...",
    "dev": "...",
    "postinstall": "..."
  }
}
```

npm scripts execute code.

Therefore npm scripts must inherit the same sandbox restrictions as any other child process.

Do not let:

```bash
npm install
```

become an unrestricted arbitrary host-code execution mechanism.

---

to escape the VFS.

Example:

Do not reset the working directory after every command within the same logical shell session.

# 7. Central Configuration Limits JSON

This is the most important architectural change in v1.0.8.

Create **one authoritative configuration-limit JSON file**.

Its purpose is:

> Define the allowed range, default, type, unit, nullability, and other metadata for every configurable NexTool setting.

A self-hosted NexTool installation should be able to customize configuration limits by editing this single JSON file instead of modifying source code.

---

# 7.1 Single Source of Truth

Create something conceptually like:

```text
config/
└── configuration-limits.json
```

Use the project's existing configuration directory conventions if one already exists.

Do not create multiple competing limit files.

---

# 7.2 Example Structure

Use a structured schema similar to:

```json
{
  "version": 1,

  "network": {
    "timeoutMs": {
      "type": "integer",
      "nullable": false,
      "default": 60000,
      "min": 100,
      "max": 3600000,
      "unit": "ms"
    },

    "maxResponseBytes": {
      "type": "integer",
      "nullable": false,
      "default": 5242880,
      "min": 1024,
      "max": 734003200,
      "unit": "bytes"
    },

    "maxRedirects": {
      "type": "integer",
      "nullable": false,
      "default": 56,
      "min": 0,
      "max": 56,
      "unit": "count"
    },

    "maxRequestsPerExecution": {
      "type": "integer",
      "nullable": false,
      "default": 56,
      "min": 1,
      "max": 56,
      "unit": "count"
    },

    "allowUrlImports": {
      "type": "boolean",
      "nullable": false,
      "default": true
    }
  }
}
```

This is an architectural example. Use the actual application's configuration naming conventions.

---

# 7.3 Every Config Property

The configuration-limit JSON must cover **all configurable properties**, not only v1.0.8 additions.

Each property should define metadata such as:

```text
type
nullable
default
min
max
unit
description
```

Optional metadata may include:

```text
step
enum
category
deprecated
requiresRestart
```

---

# 7.4 Nullable Settings

Some settings may legitimately be unlimited/disabled.

Support:

```json
{
  "nullable": true
}
```

For example, where appropriate:

```text
null = no explicit limit
```

However, never interpret `null` as unlimited automatically.

Each nullable property must define/document exactly what `null` means.

---

# 7.5 Type Safety

Supported configuration types should include:

```text
integer
number
boolean
string
enum
```

Add arrays/objects only when actually required.

---

# 7.6 Runtime Loader

Create a central configuration-limit loader.

Conceptually:

```text
configuration-limits.json
        ↓
Limit Loader
        ↓
Validated Limit Schema
        ↓
Settings Resolver
        ↓
Runtime
```

Every subsystem should consume the resolved configuration.

---

# 7.7 Startup Validation

When NexTool starts:

```text
load configuration-limits.json
 ↓
parse JSON
 ↓
validate schema
 ↓
validate default/min/max relationships
 ↓
build runtime configuration
```

If the JSON is invalid:

```text
fail clearly
```

Do not silently use random hard-coded values.

---

# 7.8 Validate Limit Relationships

For every numeric property:

```text
min <= default <= max
```

must hold.

If:

```text
default > max
```

startup/config loading must report a clear configuration error.

---

# 7.9 Self-Hosting Customization

The key requirement:

A self-hosted NexTool administrator should be able to modify:

```text
configuration-limits.json
```

to customize the maximum allowed values.

For example, if a deployment needs:

```text
tool timeout maximum = 1 day
```

the administrator should be able to change the configuration-limit JSON rather than edit TypeScript source code.

However:

**Do not assume the application's current one-hour maximum must remain permanently hard-coded.**

The v1.0.8 architecture should make the JSON authoritative.

The supplied initial configuration should contain the requested one-hour maximum:

```text
3600000ms
```

but the architecture must allow a self-hosted administrator to raise it through the single limits file.

---

# 7.10 Important Security Boundary

The configuration-limit JSON controls the application's configured limits.

It must NOT automatically grant host-level privileges.

For example:

```text
max timeout = 1 day
```

does not mean:

```text
unrestricted host process
```

and:

```text
max VFS size = 700 MiB
```

does not mean:

```text
host filesystem access
```

The security boundaries remain enforced.

# 27. Final Implementation Instruction

Implement **NexTool Q1 v1.0.8** completely.

The central architectural principle of this release is:

```text
                configuration-limits.json
                         │
                         ▼
                ┌─────────────────┐
                │ Limit Validator │
                └────────┬────────┘
                         │
                         ▼
                Runtime Configuration
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
       Settings       Backend        Runtime
                                      │
                    ┌─────────────────┼────────────────┐
                    ▼                ▼                ▼
                 Network            VFS         Execution
                    │                                 │
                    └─────────────┬───────────────────┘
                                  ▼
                              Tool Runtime
```

Every configurable limit must ultimately originate from this centralized configuration system.

Do not create a new hard-coded limit in one subsystem to solve a problem.

Do not duplicate the same setting across multiple JSON files.

Do not make the frontend the authority.

Do not make the backend and runtime use different limits.

Do not weaken the sandbox because the limits are increased.

The result should allow a self-hosted NexTool administrator to customize the platform's operational limits by editing **one configuration-limit JSON file**, while the actual application source remains unchanged.

After implementation run:

```bash
bun test
bun run lint
bun run build
```

Then manually verify:

```text
1. confirm() in both environments
2. URL import() in both environments
3. npm/node inside VFS
4. MERN-style project creation inside VFS
5. network timeout > 10 seconds
6. VFS > 8 MiB
7. execution limits
8. change one limit in JSON
9. restart NexTool
10. verify Settings + backend + runtime all use the changed value
11. Task Console has no artificial bottom whitespace
```

Do not consider v1.0.8 complete until the centralized configuration system is actually authoritative throughout the application.
